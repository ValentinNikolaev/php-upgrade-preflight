# v0.3 staged-analysis contract

This document describes the contract locked for the v0.3 development line. The normative machine-readable form is [`tests/fixtures/contracts/v0.3.json`](../tests/fixtures/contracts/v0.3.json); schema consumers must use [`upgrade-report-v0.8.schema.json`](../packages/core/resources/schema/upgrade-report-v0.8.schema.json).

## Three independent conclusions

Schema 0.8 reports three conclusions that answer different questions:

- `resolution.status` describes only the direct final-target Composer scenarios.
- `transition.framework_guidance[].status` describes only adapter rule coverage.
- `staged_resolution.status` describes only the executed adjacent-stage Composer chain.

Each dimension can be `blocked` or unsupported while another is feasible or supported. Consumers must not use one to upgrade, suppress, or infer another.

## Stages and candidate state

One active optional `FrameworkStageTargetProvider` may supply a contiguous ordered plan. The required v0.2 adapter interfaces are unchanged. Every stage contains exact package targets, an exact PHP analysis value supported by request evidence and checked against adapter minimum metadata, its execution state, resolution status, attempts, selected attempt, package changes, source assessment, and input/output fingerprints.

The analyzer starts with the original manifest and lock. Attempts run only in analyzer-owned temporary workspaces. When adapter-evidenced root remediations exist, they run in this order:

1. exact stage targets;
2. the first normalized adapter-evidenced root remediation;
3. all adapter-evidenced root remediations plus Composer's all-dependencies mode for eligible locked direct and transitive packages.

When no adapter-evidenced root remediation exists, the second and final attempt retries the exact stage targets with Composer's all-dependencies mode. Its strategy is `locked_package_remediation`.

A candidate is selectable only after a full-target Composer success and when no blocking registry entry remains active for that attempt. Its manifest, lock, effective platform, and execution policy form the next stage's input. The analyzed project is never changed.

The Milestone 0 Laravel vertical slice is deliberately narrower than ordinary Laravel guidance: it runs only for a project rooted on `laravel/framework` 10 whose only Laravel-family target is `laravel/framework` 13. Illuminate-component-only projects and mixed Laravel-family target sets remain staged guidance gaps until the provider is generalized.

## Blocker registry

`staged_resolution.blocker_registry` is always an ordered array. Every entry has stable identity, stage, first attempt and scenario, category, subject, blocking package, requested and blocking constraints, dependency path, confidence, evidence, first/last observation, lifecycle history, and current lifecycle.

The lifecycles are `detected`, `persists`, `resolved`, and `superseded`. A remediation may resolve no blockers, a subset, or several and may reveal a different blocker. Later success retains earlier records. Exact identity is deduplicated within an attempt and across attempts in one stage; entries from different stages never merge. Similar wording or package names do not merge distinct constraints, dependency paths, platforms, or stages.

## Stop and uncertainty rules

Stage execution state is `evaluated` or `skipped`, independent of its nullable per-stage resolution status. Evaluated resolution statuses are `feasible`, `feasible_with_changes`, `blocked`, and `unknown`. Missing or ambiguous targets, guidance gaps, provider conflicts, and hop-budget failures skip staged solving as unknown. Solver blockers stop as blocked. Timeouts and operational failures stop as unknown. All later planned stages are skipped; the analyzer never invents results after a stop.

The maximum scenario count is the derived product of the independently enforced hop and per-stage attempt caps. It is reported as a budget invariant, not as a separate runtime stop condition.

Only the original source snapshot is inspected. Later-stage source findings are therefore unresolved review evidence, not claims that an earlier source edit was applied.

## Platform and execution boundary

The v0.3 contract reserves versioned partial and complete target-platform profiles. Partial means unlisted platform packages may still come from the analyzer runtime. Complete means unlisted supported packages are modeled absent and requires Composer 2.2 or newer; an older Composer yields operationally unknown rather than silently weakening completeness. Milestone 0 keeps the existing explicit PHP and extension assumptions and does not claim complete-profile or restricted-execution reproducibility.

Staged solving is bounded to six hops, three attempts per stage, eighteen scenarios, 300 seconds per scenario, 1,800 seconds aggregate, 256 MiB memory, 512 KiB canonical JSON, and 256 KiB Markdown.

## Compatibility and scope

Schema 0.7 and the signed v0.2.1 artifacts remain immutable under [`tests/fixtures/contracts/v0.2.1`](../tests/fixtures/contracts/v0.2.1). See [Schema and compatibility](schema.md) for the 0.7→0.8 migration.

v0.3 does not add Symfony or CodeIgniter adapters, a PHAR, a supported runtime container, a higher PHP runtime floor, source modification, project Composer-file modification, application execution, or a runtime-compatibility guarantee.
