# Reading the first upgrade decision

These are task checklists for schema `0.8` reports. They describe how to use recorded outcomes; they are not evidence that users understood or completed an upgrade. Start with the Markdown Decision Summary or the corresponding JSON fields. Follow the cited evidence to the Composer attempt or source observation before changing the project. A report exit code of `0` says only that the report was produced.

| Report state | First subject and evidence | Limitation to retain | Next safe action | Manual validation |
| --- | --- | --- | --- | --- |
| Direct `feasible` or `feasible_with_changes` | Inspect `resolution.status`, successful scenario outcomes and their candidate-lock evidence, plus the reported `transition.package_changes`. Schema 0.8 does not mark one direct scenario as selected. Review the first `plan.stages` action and any `source_impact` evidence. | Composer found a dependency solution; it did not boot the application or test deployed behavior. Read `risk.drivers`, `effort.assumptions`, and `uncertainties` for omitted checks. | Apply and review the recorded root constraint and reported lock transition, then perform the recorded test guidance. If staged work is requested, check its separate status before advancing. | Run the project test suite, platform checks, focused migrations and deployment checks on the target runtime. |
| Direct `blocked` | Inspect the first resolution-blocking `blockers[]` subject and its `evidence` before following the dependency plan action. Advisory package findings may also be present. | A blocker is evidence for the attempted dependency state, not proof that every alternative target is impossible. Any failed scenario or source omission still limits the assessment. | Resolve the cited constraint, missing package, platform requirement, or metadata issue; rerun isolated analysis to select a candidate before changing the lockfile. | Validate the eventual candidate with Composer and project tests; review runtime and business migration work separately. |
| Direct `unknown` | Inspect scenario `outcome`, exit status, bounded diagnostics, and any `uncertainties` or input-failure evidence. A risk grade or `0-0` sentinel is not a successful assessment. | Missing Composer, timeout, unavailable metadata, invalid input, and process failure do not establish feasibility or low risk. | Repair the reported input or analysis environment, or allow the timed-out/metadata-dependent run to complete; rerun before planning a dependency transition. | After a successful candidate exists, run project and platform checks. Record unobserved migrations, deployment, runtime and business work separately. |
| Direct and staged results disagree | Read `resolution.status` and `staged_resolution.status` independently; inspect successful direct scenario outcomes and candidate-lock evidence, then each staged attempt and stop record. Only staged attempts have a serialized selection marker. | A feasible staged path does not prove direct final resolution. A successful direct solve does not clear a blocked hop. Stage source checks still use the original project snapshot. | Follow only the first executed selectable stage and its recorded action. If a stage is blocked or unknown, stop there and rerun after remediation; do not infer later-hop results. | Test the application after each applied hop and verify source changes, migrations and deployment effects before advancing. |
| Staged `skipped` or a later stage skipped | Inspect `staged_resolution.stop_reason`, `evidence`, and each `stages[].execution_state`; the first skipped stage has no selected candidate. | A skipped stage is an analysis limit, not a Composer incompatibility. Direct resolution may still have a separate valid result. | Resolve the documented plan/provider/target/PHP/budget condition, or use the direct result only for its own stated scope. Rerun staged analysis before claiming a stepwise transition. | Validate every executed hop and arrange manual review of unexecuted stages; run project tests on the target runtime. |

The `risk.level` grade rates observed findings only. Its drivers qualify incomplete or degraded analysis, and `effort.assumptions` state the uncalibrated range's scope. The staged hop, attempt, process and timeout limits are enforced. Memory and report-size values in `staged_resolution.budgets` are advisory targets without per-run peak-memory or pass measurements in schema `0.8`; missing measurements are not zero or a passed budget.
