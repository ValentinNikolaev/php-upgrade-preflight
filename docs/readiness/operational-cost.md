## Real offline Composer observations

The CLI ran in restricted mode with local path repositories and Packagist disabled by each fixture. The root checkout had installed dependencies; Docker image creation, dependency installation, container startup, discovery and report reading were outside the measured CLI wall time. `COMPOSER_ROOT_VERSION=1.0.0` was set. Scenario timeout was **15 seconds** and diagnostic timeout **5 seconds** for these bounded probes, rather than the shipped defaults of 300 and 60 seconds. A temporary executable wrapper logged each Composer invocation before `exec /usr/local/bin/composer "$@"`; the wrapper was removed after each run. These counts are instrumented Composer invocations, not all OS descendants Composer might spawn. The JSON and Markdown byte counts came from separate CLI executions with the same request. PHP peak is `memory_get_peak_usage(true)` in the analyzer CLI process, including the one-off measurement wrapper; it measures allocated PHP heap, **not** child Composer RSS, container peak, or an application's memory. Those peaks remain unmeasured.

The one-off PHP measurement harness called the CLI application with these exact argument templates; substitute `json` and `markdown` for `{format}` in separate runs. It created executable `/tmp/preflight-r4-composer-proxy-{pid}`, appended each argument vector as one line to `/measure/{case}.{format}.calls`, then delegated to `/usr/local/bin/composer`. Its `/measure` mount was a task-owned OS temporary directory, and it removed the proxy after measuring. The target fixture was read directly; reports were written outside it.

```text
upgrade-intel analyze --path=/app/tests/fixtures/path-repository/project --composer-mode=restricted --composer-executable=/tmp/preflight-r4-composer-proxy-{pid} --composer-timeout=15 --composer-diagnostic-timeout=5 --format={format} --output=/measure/small.{format}.report --target=fixture/dependency:^2.0
upgrade-intel analyze --path=/app/examples/five-minute-demo/target --composer-mode=restricted --composer-executable=/tmp/preflight-r4-composer-proxy-{pid} --composer-timeout=15 --composer-diagnostic-timeout=5 --format={format} --output=/measure/staged.{format}.report --from-php=8.1 --target=laravel/framework:^13.0 --target-php=8.3 --without-extension=ext-preflight-stage --framework=laravel
```

The demo's JSON run made six direct scenarios and seven staged attempts across three stages. Its nine direct Composer calls comprise six scenarios and three distinct diagnostics; 21 staged calls comprise seven scenarios and 14 diagnostics. The report records seven direct diagnostic *entries*, four of which reused cached diagnostics and spawned no new child. Sum of report scenario durations was 2.533 s direct and 5.184 s staged; those sums are not an independent whole-run wall measurement. No scenario timed out or had an unknown Composer outcome in these two JSON runs. The small run had four successful direct scenarios and no diagnostic calls. The staged demo had two direct successes/four direct solver failures and two staged successes/five staged solver failures. Both commands exited 0 because a valid report was produced, including for blocked resolution.

For each of the four measured executions, a sorted SHA-256 digest of relative paths and file hashes was identical before and after: `2a0418fba46deebb8ebf1e9979da92eabd49a531b4a2f958fe9348441cf5c6e5` for the small target and `cc958cdbdb84372a244aa352bc414756aa5b6736497113ed3594c2a00f2eafc2` for the demo target. The analyzer's `/tmp/php-upgrade-preflight-*` directory set gained no retained directory during any run; debug preservation was not requested. These are fixture immutability and observed cleanup checks, not a proof about unknown external applications.

The demo is a deliberately small **synthetic application model** built from local Composer metadata. The existing `RepresentativeCorpusBudgetTest` uses a fake Composer callback, and `WorstCaseStagedBudgetTest` fabricates solver results through its process callback for a six-hop fixture. The latter checks orchestration bounds, determinism, redaction, report size and input immutability, but its process count is callback invocations, not real OS children; its runtime is not a real six-hop Composer benchmark. Both budget tests passed locally (2 tests, 932 assertions). No real six-hop application-scale profile was obtained. Networked repository access, Composer caches, global configuration and live package metadata can change operational cost; these offline results exclude that variance.

The published [application evaluation](../laravel-coverage/application-evaluation.md#execution-immutability-and-reproduction) recorded Lychee exhausting a 128 MiB PHP limit before a valid report, followed by a valid 1024 MiB rerun under changed repository access. Its [machine record](../laravel-coverage/application-evaluation.json) retains only tool output for the failed attempt, not a report body or profiler trace. The failed process's allocation site, whether it was the analyzer or a child, the effective input/cache state and the minimum successful limit cannot be recovered from that record. The small current-fixture peaks do not explain or overturn the Lychee result. A pinned Lychee reproduction with separate analyzer and child memory profiles, exact network/cache state, and a successful/failed limit pair is needed before assigning cause or a deployment minimum. In particular, the serialized **256 MiB memory, 512 KiB JSON and 256 KiB Markdown** values remain advisory targets, not enforced guarantees. The six-hop, three-attempt, 128-process and 300/900/1,800-second staged caps remain enforced as described in the contract; no optimization or cap change is justified by these measurements alone.

## CI and maintenance exposure

The existing three-package [Quality run 37833309503](https://github.com/ValentinNikolaev/php-upgrade-preflight/actions/runs/37833309503) at `b63d83ebf622cbff49916c2734430c4a0298485a` succeeded on 2026-10-08. The run's `createdAt` to `updatedAt` elapsed time was **7 minutes 34 seconds**. Summing `completedAt - startedAt` for each **non-skipped step** yields 1,302 seconds across 10 Linux jobs and 1,606 seconds across nine Windows jobs: **2,908 unweighted runner-seconds** (48 minutes 28 seconds). Summing job start-to-completion envelopes yields 1,365 + 1,629 = 2,994 seconds. The 86-second difference includes gaps outside recorded successful steps, including 37 seconds in the coverage job; neither figure is an invoice or an account-specific billed-minute calculation. Parallel job durations must not be confused with workflow wall time. This run is the Quality workflow, not every scheduled/release workflow.

Separately, the three-package [Compatibility smoke run 37696577324](https://github.com/ValentinNikolaev/php-upgrade-preflight/actions/runs/37696577324) at `dd86c687882d11084e436001d0a27246935e4ebc` succeeded on 2026-10-07 in **33 seconds** from `createdAt` to `updatedAt`. Its 15 cases × normal/lowest resolution produced 30 Linux jobs: 434 summed non-skipped step-seconds and 508 job-envelope seconds. Jobs ranged from 10 to 25 step-seconds in that run. It uses live Composer metadata, so this timing cannot be combined with the later Quality run as a same-revision end-to-end baseline or guaranteed future duration. Cache hits, network, runner type, concurrency, billing allocation, rates and account allowances were not established; **cash cost is unknown**.

A fourth published adapter would add one package archive/distribution repository and a fifth Wiki destination to the current four. Applying the observed 10–25 step-seconds per job gives a conditional **20–150 extra step-seconds for that smoke slice only**. New adapter assertions would also run through the six Linux PHP runtime jobs and the Windows test partitions; their duration increase is unmeasured. Catalog review requires checking every approved hop and its exact PHP/component constraints against source, refreshing pinned guide evidence and fixtures, plus one more Wiki manifest, rendered pages, remote review/publication and release evidence. Maintainer hours/capacity for that work, a day rate, and any resulting financial cost are unavailable. R3 has no measured setup, run, reading or planning-time benefit from users, so there is no defensible net-time, 20% benefit, or return-on-effort comparison.

## Scope consequence

No Symfony owner cases have been supplied. A minimum supported application/component shape and family-staging requirement therefore remain **unselected**. The safe prospective contract is one unambiguous stage provider with explicit refusal on a provider or rooted-family conflict, preserving every requested target and evidence ownership; there is no case for adding broad multi-provider staging machinery now. If owner cases later prove a same-major Symfony hop or multiple rooted components, define the narrow version/family contract from those cases before implementation. The current [stage plan resolver](../../packages/core/src/Analysis/StagePlanResolver.php) already refuses multiple providers; this record changes no published behavior.

R4 remains **partially measured**: the tiny real offline costs and CI timing proxies are known, while production-scale memory, live-network cost, maintainer capacity and user benefit are unavailable. [R5 explicitly recorded `VALIDATE_FIRST`](release-direction.md) and deferred Symfony; these empirical gates remain open.
